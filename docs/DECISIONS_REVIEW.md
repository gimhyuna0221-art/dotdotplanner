다음은 판정 대상이 아니다.

## 3. 검토 중 확인된 사실

### 3.1 문서가 코드보다 뒤처져 있다

`01_PRODUCT_DEFINITION.md`는 루틴·단축키·검색·통계·설정을 "아이콘만 있고 기능 연결이 완료되지 않았을 수 있다"로 기록하고, `03_SCREEN_SPEC.md`는 24시간 축을 "아직 구현하지 않는다"로 기록한다.

실제로는 전부 동작하는 코드가 들어와 있다.

- `dotdot-extensions.js`가 24시간 정밀 모드(자정 넘김, 다일 연속 렌더, 드래그 이동·경계 리사이즈), 루틴, 단축키, 검색, 통계, 설정, 로컬 프로필을 구현한다.
- `app.js`가 `monthlyLogViewMode`, `defaultInputMode`, `autoRolloverEnabled`를 정식 상태·저장 키로 취급한다(`app.js:143-148`, `app.js:1023-1060`, `app.js:1145-1147`).
- `index.html:2566-2567`에 `자유 배치` / `24시간` 보기 토글이 있다.

따라서 이번 검토는 "만들지 말지"가 아니라 **"이미 들어온 것을 남길지 뺄지"** 다.

### 3.2 루틴과 이월이 충돌해 항목이 누적된다

`getAutoRolloverCandidateIds()`는 미완료 `task`를 전부 이월 후보로 잡으며 `routineId`를 모른다(`app.js:3535-3545`).
`materializeDueRoutines()`의 중복 방지는 `routineId + routineDate` 쌍으로만 판정한다(`dotdot-extensions.js:566`).

결과: 어제 루틴을 끝내지 않으면 그 항목이 오늘로 이월되고, 동시에 오늘치 루틴이 새로 생성된다. 이월된 항목의 `routineDate`는 어제이므로 중복 방지에 걸리지 않는다. 같은 할 일이 하루에 하나씩 누적되고, 사용자가 손으로 지워야 한다. **3원칙 2번 정면 위반이다.**

### 3.3 루틴 생성 경로가 공식 저장 경로를 우회한다

`materializeDueRoutines()`는 `state`를 거치지 않고 `localStorage`의 `items` 키를 직접 읽고 쓴 뒤 `location.reload()`를 호출한다(`dotdot-extensions.js:561-573`).

- Undo/Redo 대상이 아니다.
- `dataRevision`을 올리지 않아 교차 탭 충돌 감지가 이 변경을 인지하지 못한다.
- **메모리와 저장소의 상태 불일치 위험이 있다.** 저장 실패 자체가 덮어쓰기의 원인은 아니다. 정확한 경로는 이렇다 — `localStorage` 직접 저장이 **성공한** 뒤 `reload`가 중단되면(사용자가 이동·중단하거나 예외로 흐름이 끊기는 경우), 메모리의 `state.items`는 루틴 항목이 없는 낡은 상태로 남는다. 이후 앱의 정상 조작이 `saveItems()`를 호출하면 그 낡은 배열이 직접 저장분을 덮을 수 있다.
- `routineId`, `routineDate`는 `02_DATA_SPEC.md`에 없는 필드다.

## 5. 판정 상세

### 5.1 Monthly Log 18칸 — 수동 유지, 자동은 별도 모드

사용자 확인 결과 **가로 위치에는 의미가 없다.** 일정끼리 겹치지 않게 빈 칸에 놓을 뿐이며 칸 번호를 기억하지 않는다.

의미 없는 축에 손으로 배치하는 행위는 기록이 아니라 겹침 회피 노동이므로 3원칙 2번과 Q4에 걸린다. 방향으로는 자동 배치가 옳다.

다만 **이번 검토에서 자동 배치를 즉시 적용하지 않는다.**

- `dotdot-extensions.js:180-190`의 `assignLanes()`는 1차원 구간 그리디 패킹이다. 입력이 절대 분 단위 `start`/`end`인 시간축 전용이다.
- 18칸 월간 뷰의 다일 항목은 여러 날짜 행을 세로로 관통하는 같은 열 블록이다. 열 × 날짜 행의 2차원 배치 문제이며 알고리즘이 그대로 옮겨가지 않는다.
- 따라서 자동 배치는 **수동 모드를 대체하지 않는 별도 모드**로 추가하고, 기존 저장 위치와 롤백 경로를 유지한다.

확정 사항:

- 수동 18칸 모드는 그대로 둔다. 하드 스냅, 히스테리시스, 마퀴, Ctrl+휠 행 높이, Shift+휠 셀 너비, 자유 구분선 모두 유지한다.
- **확정:** 자동 배치 모드는 `monthlyLogScheduleColumn`·`monthlyLogLaneIndexByDate`에 **쓰지 않는다.** 모드를 껐다 켜면 수동 배치가 그대로 돌아와야 한다.
- **설계 단계로 남김:** 그 필드를 **읽어서** 자동 배치의 정렬·안정화 기준(예: 기존 수동 위치가 가까운 순서를 유지하는 tie-break)으로 쓸지는 아직 정하지 않는다. 읽기는 저장값을 바꾸지 않으므로 롤백 위험이 없지만, 자동 결과가 수동 배치에 얼마나 끌려가야 하는지는 패킹 규칙과 함께 정해야 한다.
- 세 보기(수동 18칸 / 자동 배치 / 24시간)는 같은 `state.items`를 읽는 표현 모드로만 병존한다. 어느 것도 다른 것의 저장 필드를 덮어쓰지 않는다.

### 5.2 18칸과 24시간을 합치지 않는다

18칸의 가로축은 무의미하고 24시간의 가로축은 시간이다. 하나로 합치면 자유 배치가 시간 조작으로 오독되어 Q5 정면 위반이다. 둘 중 하나를 버리는 것도 채택하지 않는다.

- 24시간 모드는 `eventsForDate()`가 `item.type !== 'schedule'`을 전부 제외한다(`dotdot-extensions.js:196-198`). 할 일과 메모가 이 보기에 나오지 않는다.
- 의도된 설계라도 화면에 안내가 없으면 데이터가 사라진 것으로 오인된다. **"이 보기는 일정만 표시합니다"를 화면에 정직하게 표시한다.**

기본값 규칙:

- 저장값이 없을 때만 `lanes`가 기본이다.
- 사용자가 선택한 마지막 모드를 기억한다.
- 현재 코드가 이미 이 규칙대로 동작한다(`app.js:1023-1025`가 저장값 없으면 `lanes`, `app.js:1145`가 선택을 저장, 토글이 `B.savePreferences()` 호출 — `dotdot-extensions.js:625`). 따라서 이 항목은 **변경이 아니라 유지·확인 대상**이다.

### 5.3 이달의 할 일 — 입구와 배치 루프를 분리한다

두 가지를 하나로 묶어 판정하지 않는다.

**입구(날짜 없는 수집함)는 실사용이 확인됐다.** 유지하며 이 제품의 핵심 진입점으로 취급한다.

**날짜 배치 루프는 실사용이 검증되지 않았다.** 기능은 동작하지만 사용자가 거의 쓰지 않았다. 제품 정의 5.2의 "시간 범위에 따른 점진적 구체화"가 실제로 도는지 아직 증거가 없다.

따라서:

- 배치 루프를 삭제하지 않는다. 증거 없이 걷어내면 되돌리는 비용이 훨씬 크다.
- 배치 루프 주변 기계(`sourceMonthlyItemId` 공유 필드 동기화, `instanceGroupId` 연결 인스턴스, 배치본 휴지통 동기화)도 손대지 않는다. 이것은 **과잉이 아니라 검증 미완 투자**다.
- 이 루프에 대한 신규 확장·최적화 투자를 중단하고, 사용 관찰을 먼저 한다.

### 5.4 과거 미완료 수집함의 접근 경로

현재 `getOverdueMonthlyItemIdsForMonth()`는 **바로 전 달만** 조회한다(`app.js:3522-3530`).

정확한 표현은 다음과 같다. 오래된 `monthlyItem`은 **해당 과거 월로 직접 이동하면 접근할 수 있다.** 도달 경로가 없는 것이 아니다. 문제는 **현재 월에서의 통합 발견 경로와 검색 경로가 없다는 것**이다.

- 2개월 이상 지난 미완료 마스터는 현재 월의 "지난달 미완료" 영역에 나오지 않는다.
- 검색이 `getAliveItems()` = `state.items`만 조회하므로 `monthlyItems`는 검색으로도 잡히지 않는다(`dotdot-extensions.js:583`).
- 결과적으로 사용자가 그 달을 기억해서 직접 찾아가야만 한다. 성공 기준 "완료와 과거 기록을 다시 찾을 수 있다"에 미달한다.

**확정 — 발견·조회**

기간 제한 없이 **모든** 과거 미완료 마스터에 적용한다. 3개월 이상 지난 항목도 예외가 아니다.

1. 모든 과거 미완료 마스터를 **월별 접이식**으로 표시한다. 바로 전 달 한정을 해제한다.
2. 검색에 `monthlyItems`를 포함한다.

**미확정 — 3개월 이상 항목의 처분 정책**

미확정인 것은 발견·조회가 아니라 **처분**뿐이다. 다음 세 가지는 이 문서가 정하지 않는다.

- 자동 이동(오래된 마스터를 현재 달로 옮길지)
- 보관(별도 보관 상태로 분리할지)
- 정리(일괄 완료·삭제·숨김을 제공할지)

이 구분이 중요하다. **보이게 하는 것은 확정이고, 손대는 것은 미확정이다.** 처분 정책이 정해지지 않았다는 이유로 조회까지 막으면 성공 기준 "완료와 과거 기록을 다시 찾을 수 있다"를 계속 위반한다.

표현 제약:

- 자동 이동을 하지 않는다. 사용자가 정하지 않은 정책을 코드가 확정하는 것은 `CLAUDE.md` 8절 제품 금칙이다.
- 개수 배지에 경고색·느낌표·연체 문구를 쓰지 않는다(3원칙 3번).

### 5.5 통계 — 완료 표현

**삭제한다:** 완료율 `%`, 게이지 바, 그리고 **분모 자체**.

삭제 근거는 두 겹이다.

1. **원칙 위반.** 게이지 바는 "채워야 할 것"의 시각 문법이다. 100%가 목표로 읽히고 미완료가 빈 공간, 곧 실패로 표현된다. `01_PRODUCT_DEFINITION.md` 8절 설계 금칙의 "스트릭과 빈 날짜 압박"과 같은 계열이며, 코드 주석이 "성과 압박용 스트릭은 만들지 않습니다"라고 적어둔 것과 모순된다.
2. **수치가 틀렸다.** `period()`가 `items` 전체를 분모로 잡는다(`dotdot-extensions.js:584`). `memo`와 `divider`는 완료 개념이 없다 — `app.js:3526`이 `divider`를 월간 이월 대상에서 제외하는 것과 같은 이유다. 메모를 10개 쓰면 완료율이 그만큼 떨어진다. **기록을 많이 할수록 낮아지는 지표**는 이 제품에서 만들 수 있는 최악의 숫자다.

**대체안 — 절대 수와 실제 목록만.**

집계 규칙:

| 항목 | 규칙 |
|---|---|
| 대상 기간 | 기존 구간(최근 7일·30일)을 그대로 유지한다. 이번 변경은 구간이 아니라 집계 규칙과 문구다 |
| 포함 대상 1 | `type === 'task'`이고 `deletedAt`이 없고 `completed === true`이며 **`date`가 기간에 속하는** 항목 |
| 포함 대상 2 | `type === 'schedule'`의 **완료 occurrence** — **occurrence 날짜**가 기간에 속하고 `isOccurrenceCompleted()`가 참인 것 (`app.js:27900`에서 브리지로 이미 노출됨) |
| 제외 | `memo`, `divider`, 삭제 항목 |
| 출력 | 개수와 목록. 비율·게이지·분모 없음 |

기간 판정 기준은 종류마다 다르다. **`task`는 `date`, `schedule`은 occurrence 날짜**다. 하나로 합치지 않는다.

**표현 제약(중요):** 현재 데이터에 `completedAt`이 없다. 언제 완료했는지 알 수 없다.

- **"최근 완료", "이번 주에 완료함" 같은 표현을 쓰지 않는다.**
- 화면 문구는 **"계획일 기준 완료 상태"**로 명시한다.
- 기간 필터가 완료 시각이 아니라 계획일을 기준으로 한다는 사실이 화면에서 읽혀야 한다.

### 5.6 통계 — 날짜 이동 흔적

건수 하나(`moved`)는 해석할 수 없는 KPI 숫자다. 목록으로 교체한다.

**표현 제약(중요):** 현재 데이터에 이동 시각 기록이 없다. 언제 옮겼는지, 몇 번 옮겼는지 알 수 없다.

- **"최근 계획 변경", "언제 이동했는지"를 주장하지 않는다.**
- 현재 데이터로 확인 가능한 것은 `originalDate`(최초 계획 날짜) 또는 `migratedFrom`(직전 날짜)과 현재 `date`뿐이다.
- 따라서 출력은 **`원래 날짜 또는 직전 날짜 → 현재 날짜` 목록**으로 제한한다.
- 목록 정렬 기준을 "변경 시각순"이라고 부르지 않는다.
- 이동을 실패나 지연으로 서술하지 않는다. 계획 복구는 이 제품의 기능이지 결함이 아니다(3원칙 3번).

### 5.7 검색 — 조회 범위와 이동 규칙

**조회 대상 컬렉션**

- 활성 `state.items`
- 활성 `state.monthlyItems`
- 삭제된 `state.items`(휴지통)
- 삭제된 `state.monthlyItems`(휴지통)

**검색 필드**

- 제목(`text`)
- 설명(`description`)
- 프로젝트명(`projects[].name` — 레코드에 복제하지 않고 `projectId`로 조회)
- 하위 할 일(`subtasks`)

**이동 규칙 (명시)**

| 검색 결과 종류 | 열리는 곳 |
|---|---|
| 활성 `item` | Today |
| 활성 `monthlyItem` | 해당 월의 이달의 할 일 |
| 삭제된 `item` | 휴지통 |
| 삭제된 `monthlyItem` | 휴지통에서 해당 월간 마스터를 열고 선택·강조 |

**삭제된 `monthlyItem`의 이동 규칙 (확정)**

- 휴지통을 열고 해당 월간 마스터를 **선택·강조**한다.
- **자동 복원하지 않는다. 복사본을 만들지 않는다. 배치본을 생성하지 않는다.**
- 직접 포커스가 불가능하면, 휴지통을 열고 해당 항목이 보이도록 필터링하는 수준까지만 구현한다.

**제약**

- 검색 결과는 원본 항목을 가리킨다. **복사본을 만들지 않는다.**
- 결과 행에 종류(날짜 항목 / 월간 수집함 / 휴지통)를 구분해 표시한다. 어디로 이동하는지 클릭 전에 알 수 있어야 한다.

### 5.8 `[다음 달]` 이동 동작

미래로그는 별도 화면 없이 **이동 동작 하나**로 채택한다.

**정의:** 대상은 `monthlyItem` 자신의 `monthKey` **+ 1개월**이다. 현재 보고 있는 달을 기준으로 하지 않는다.

**보존 요구**

- `id`
- 제목·유형·설명·설명 블록·하위 할 일
- 첨부
- 연결 정보(`sourceMonthlyItemId`로 이어진 배치본, `instanceGroupId`)
- `projectId`
- `createdAt`

**부수 처리**

- 이동 대상 달 기준으로 무효가 된 월간 그룹 소속은 해제한다(그룹이 없거나 그룹의 `monthKey`가 다른 경우).
- **기존 배치본 정책을 임의로 바꾸지 않는다.** `state.items`의 배치본은 `date`가 독립 필드이므로 건드리지 않는다.
- Undo **한 단계**로 되돌아가야 한다.

**구현 메모:** `moveMonthlyItemsToMonth(itemIds, targetMonthKey)`(`app.js:20632-20655`)가 위 요구를 이미 전부 만족한다. `withHistoryTransaction`으로 감싸여 있고, 무효 그룹을 해제하며, 배치본을 건드리지 않는다. 필요한 것은 `getPreviousMonthKey()`(`app.js:3512`)의 대칭 함수와 버튼 하나다.

### 5.9 루틴 — 숨김 범위

**제거 대상은 세 곳뿐이다.**

1. 사이드바 진입점(루틴 화면 진입)
2. `boot()`의 자동 `materializeDueRoutines(...)` 호출
3. 수동 생성 접근(`routine-materialize`, `routine-add` 등 생성 경로)

**보존 대상**

- `localStorage`의 `routines` 데이터. **삭제하지 않는다.**
- 이미 생성된 `routineId`를 가진 항목. 일반 할 일로서 그대로 이동·완료·삭제된다.

숨기는 이유는 기능이 나쁘기 때문이 아니라, 공식 상태·Undo/Redo·`dataRevision` 경로로 통합되기 전까지 3.2와 3.3의 누적·유실이 계속되기 때문이다. 재구현 설계는 별도 라운드에서 다룬다.

### 5.10 로컬 프로필 — 확장만 제거

**제거 대상**

- Round D의 프로필 확장 이벤트 배선(`paintProfile`, 클릭·키보드 핸들러, `account` 사이드 뷰)
- `localProfile` 저장 키

**보존 대상**

- **`index.html:2375`의 원본 요소 `<div class="profile">현아</div>`를 삭제하지 않는다.**

판정 근거: Q1 기록 속도와 무관, Q2 재입력 감소와 무관, Q3 계획 연속성과 무관, Q4 새 설정 항목만 추가, Q5 무해하나 무익. 5문항 전원 불통과다.

### 5.11 백업·초기화 문구의 정직성

`import-full`과 `reset-all`은 `localStorage`의 `dotdotplanner:v1:` 접두사 키만 다루고 **IndexedDB 첨부 바이너리는 그대로 남긴다**(`dotdot-extensions.js:604-605`). 가져오기·초기화 후 첨부가 고아로 남는다.

**요구 사항**

- 내보내기·백업·가져오기·초기화 **버튼 자체에 "첨부 원본 제외"를 직접 표시한다.** 하단 안내 문구로만 처리하지 않는다.
- **IndexedDB가 남는 기능을 "모든 로컬 데이터 초기화"라고 부르지 않는다.** 실제로 지우는 범위를 이름에 반영한다.
- 확인 절차에도 첨부 원본이 남는다는 사실을 명시한다.

이것은 `01_PRODUCT_DEFINITION.md` 5.6 "로컬 데이터 신뢰"와 성공 기준 "데이터 저장 실패를 사용자가 인지할 수 있다"의 연장이다. 실제 첨부 백업 구현은 이번 범위 밖이며, 정책 확정 전까지 `CLAUDE.md` 12절에 따라 코드를 쓰지 않는다.

## 9. 앞으로 2주 구현 우선순위

전제: 1인 개발, 무료 도구만 사용. 새 도구를 도입하지 않고 기존 `node --check app.js` + Playwright/Chromium만 쓴다.
순서 원칙: **되돌릴 수 없는 손실 → 정직성 → 마찰** 순.

### 1주차 — 안전과 정직

| 일 | 작업 | 합격 기준 |

| D1 | 루틴 숨김. 진입점·`boot()` 자동 호출·수동 생성 접근만 제거. `routines` 데이터와 기존 생성 항목 보존 | 루틴 항목 신규 생성 0건, 3.2 중복 재현 불가, `routines` 키 잔존 확인, 콘솔 오류 0 |

## 11. 표현 규칙 (구현 시 준수)

이 문서의 결정을 구현할 때 다음 표현 규칙을 깨지 않는다.

### 없는 데이터를 주장하지 않는다

| 금지 | 이유 | 대체 |
|---|---|---|
| "최근 완료", "이번 주에 완료함" | `completedAt`이 없어 완료 시각을 알 수 없다 | **"계획일 기준 완료 상태"** (`task`는 `date`, `schedule`은 occurrence 날짜) |
| "최근 계획 변경", "언제 이동했는지", 이동 횟수 | 이동 시각 기록이 없다 | `원래 날짜 또는 직전 날짜 → 현재 날짜` 목록 |
| 목록을 "변경 시각순"이라 부르기 | 시각 데이터가 없다 | 정렬 기준을 사실대로 표기 |
| "모든 로컬 데이터 초기화" | IndexedDB 첨부가 남는다 | 실제 삭제 범위를 이름에 반영 + "첨부 원본 제외" |

### 죄책감을 만들지 않는다

- 완료율, 게이지 바, 분모, 스트릭, 빈 날짜 압박을 만들지 않는다.
- 미완료 개수 배지에 경고색·느낌표·연체 문구를 쓰지 않는다.
- 날짜 이동을 실패나 지연으로 서술하지 않는다. 계획 복구는 이 제품의 기능이다.

### 사용자가 정하지 않은 정책을 코드가 확정하지 않는다

- 과거 미완료 수집함을 자동으로 이동시키지 않는다.
- 3개월 이상 누적 미완료의 **처분 정책**(자동 이동·보관·정리)은 미확정이다. 이 문서는 그 정책을 정하지 않는다.
- 단, **발견·조회는 확정이다.** 처분이 미확정이라는 이유로 조회를 막지 않는다. 보이게 하는 것과 손대는 것을 혼동하지 않는다.

## 12. 이번 세션이 확정하지 않은 것

- 3개월 이상 누적 미완료의 **처분 정책**(자동 이동·보관·정리). 발견·조회는 §5.4에서 확정했다
- 자동 배치 모드의 2D 패킹 규칙, 그리고 수동 위치 필드를 **읽어서** 정렬 기준으로 쓸지 여부
- 열별 개별 너비의 폐기 여부(폐기 후보 상태, §8)
- 루틴의 공식 경로 재구현 설계
- IndexedDB 첨부를 포함한 완전 백업·가져오기 충돌 정책
- 자정 넘김 다일 시간 일정의 장기 데이터 모델
- AM/PM 없는 숫자 시간 입력 해석

이 항목들은 `CLAUDE.md` 12절에 따라 선택지·데이터 영향·회귀 위험을 제시한 뒤 사용자의 결정을 받는다.
