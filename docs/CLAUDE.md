최종 업데이트: 2026-07-31

이 파일은 개발할 때 항상 지켜야 하는 규칙이다.

## 3. 기술 제약

### 유지

- 바닐라 HTML/CSS/JavaScript
- 정적 단일 페이지
- `file://`에서도 동작
- 서버·계정·외부 API 없음
- ES Module import·런타임 fetch 의존 없음
- 구조화 데이터는 localStorage
- 첨부 바이너리는 IndexedDB
- 번들된 `korean-lunar-calendar`는 현재 `app.js` 안에 포함
- Pretendard는 로컬 자산 사용
- 현재 실제 파일 구조는 `index.html` + `app.js` 중심

### 금지

- 요청 없이 프레임워크 도입
- 빌드 도구·번들러 전환
- CDN 런타임 의존 추가
- 서버나 로그인 추가
- 기존 파일을 임의로 여러 모듈로 분리
- 대규모 리팩터링
- “깔끔해 보인다”는 이유만으로 기존 동작 재작성
- 현재 번들 라이브러리 내용 임의 수정

기술 구조 변경이 꼭 필요하면 코드를 쓰기 전에 이유·대안·마이그레이션 위험을 보고한다.

## 4. 작업 범위 규칙

### 한 번에 하나의 명확한 범위

요청받은 항목만 수정한다.

- 관련 없는 디자인 보정 금지

- 저장 스키마 변경 금지

### 기존 완료 기능을 보존

특히 다음을 되돌리지 않는다.

- `Math.round + 0.15 데드존` 히스테리시스
- 자동 스크롤 마퀴 좌표 보정
- 가로·세로·대각선 범위 생성
- 기존 일정 마퀴 다중선택
- Daily·Weekly 일반 드래그
- 프로젝트 색과 연결선
- 월간 마스터·배치 동기화
- 연결 인스턴스 동기화
- 그룹·복사·휴지통
- Undo/Redo
- 완료 숨기기·완료 정리
- Ctrl+휠 행 높이
- Shift+휠 셀 너비
- 날짜칸 초기화 메뉴
- JSON export·마이그레이션 백업의 projects 포함

## 5. 사용자 용어 해석

### “스냅”

사용자가 말하는 스냅은 드롭 후 보정이 아니다.

> 드래그 중 미리보기 자체가 셀 경계를 넘을 때만 칸에서 칸으로 움직이는 실시간 하드 스냅.

마우스를 자유롭게 따라가다가 놓는 순간만 정렬하는 방식은 불합격이다.

### “상호 이동”

단순 복사가 아니라 동일 항목을 다른 날짜·화면으로 이동하는 것을 우선 뜻한다.  
월간 마스터 배치처럼 복사본이 필요한 경우에는 원본 유지와 연결 규칙을 명시한다.

### “완료”

완료와 삭제를 혼동하지 않는다.  
숨기기는 표시 설정이며 데이터 삭제가 아니다.

## 6. 데이터 안전 규칙

- 변경 전 백업 생성
- items·monthlyItems·groups·projects를 함께 고려
- 저장 대상별 오류 배너 독립성 유지
- 손상 데이터를 조용히 버리지 않음
- 마이그레이션 전 원본 백업
- export에 새 핵심 컬렉션 누락 금지
- 휴지통 항목도 연결 필드 동기화 대상인지 확인
- 날짜·시간을 임의 추측하지 않음
- schemaVersion을 올릴 때 순차 마이그레이션 추가
- ID 충돌과 연결 참조를 무시한 병합 금지

스키마를 추가·변경해야 하는 작업은 먼저 논의하고 멈춘다.

---

## 7. UI·상호작용 규칙

- 주요 입력은 항상 접근 가능
- 화면마다 같은 조작은 같은 의미
- 입력 중 IME 중복 생성 방지
- 텍스트 입력 중 앱 단축키가 기본 편집을 방해하지 않음
- selection은 데이터가 아니라 세션 상태
- 마퀴·드래그 테스트는 하드코딩 픽셀보다 DOM rect 사용
- 자동 스크롤이 들어가면 뷰포트 좌표와 콘텐츠 좌표를 혼용하지 않음
- resize·스크롤·드래그 리스너는 종료 시 정리
- 포인터 캡처·Escape·pointercancel 경로 보장
- 가로 문서 스크롤과 화면 밖 잘림 금지
- 좁은 화면에서 기능을 제거해 문제를 숨기지 않음

## 8. 제품 금칙

- 미완료를 실패·연체로 낙인
- 스트릭과 빈 날짜 압박
- 입력 전 프로젝트·분류·우선순위 강제
- 완료·저장 후 불필요한 확인
- 화면마다 다른 생성 규칙
- 주요 조작을 호버에만 숨기기
- 시간 블록 임의 자동 보정
- 사용자가 정하지 않은 정책을 코드가 대신 확정
- 테스트 통과를 위해 assertion 완화
- 실패한 테스트를 “기존 문제”라고만 하고 기능 검증을 끝내지 않기

## 9. 테스트 규칙

### 최소 필수

```bash
node --check app.js
```

추가로 반드시 수행한다.

1. 수정 기능 전용 Playwright 테스트
2. 관련 기존 회귀 스위트
3. 콘솔 오류 확인
4. 페이지 오류 확인
5. Undo/Redo가 관련되면 전·후 데이터 비교
6. 저장 변경이면 실제 localStorage 또는 Blob payload 확인
7. 레이아웃이면 여러 viewport 검증
8. 드래그면 시작·중간·종료 좌표와 결과 필드 확인

### 테스트 실패 시

1. 실패를 숨기지 않는다.
2. 백업본과 현재본에 같은 재현을 실행한다.
3. 테스트 결함과 앱 결함을 분리한다.
4. 좌표 테스트는 DOM `getBoundingClientRect()`로 재작성한다.
5. 목표 ID와 디코이 제외까지 검증한다.
6. 실제 앱 결함이면 관련 함수만 최소 수정한다.
7. 전체 회귀를 다시 실행한다.

### 완료 판정

“코드가 있다”와 “기능이 검증됐다”를 구분한다.

- 자동 테스트 완료
- 사용자 수동 재검증 필요
- 설계 보류
- 실행하지 못함

상태를 섞지 않는다.
