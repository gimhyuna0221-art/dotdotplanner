# 01. 제품 정의 — DotDotPlanner

최종 업데이트: 2026-07-31  
문서 역할: 무엇을 왜 만드는지, 누구를 위한 제품인지, 어떤 기능을 채택하거나 거절하는지 규정한다.

---

## 1. 제품 정의

닷닷플래너는 한 번 입력한 기록을 Today·Weekly·Monthly Log·이달의 할 일에서 재입력 없이 이동·배치·완료·회고할 수 있는 개인용 로컬 퍼스트 플래너다.

제품의 핵심은 화면을 많이 제공하는 것이 아니라, **같은 기록이 시간 범위에 따라 다른 방식으로 보이면서도 정체성을 잃지 않는 것**이다.

- 먼 계획은 `이달의 할 일`에서 날짜 없이 시작할 수 있다.
- 월간 흐름은 `Monthly Log`에서 시각적으로 배치한다.
- 가까운 일정은 `Weekly`에서 날짜 간 관계를 본다.
- 오늘 실행은 `Today`에서 상세하게 처리한다.
- 설명·하위 할 일·미디어는 같은 항목의 상세 맥락으로 유지한다.

## 2. 타깃

### 핵심 타깃

**한국 플래너 유목민**

- 플래너를 반복해서 바꾸지만 정착하지 못한다.
- 처음부터 완벽하게 분류하거나 계획하는 데 부담을 느낀다.
- 계획이 틀어졌을 때 다시 작성하는 비용이 크다.
- 완료한 기록이 사라지는 도구에 성취감을 느끼기 어렵다.
- 여러 화면에 같은 내용을 다시 입력하고 싶지 않다.
- 협업 도구보다 개인의 실제 생활 흐름에 맞는 도구가 필요하다.

### 비타깃

다음이 핵심 요구인 사용자는 주 타깃이 아니다.

- 조직 협업과 담당자 배정
- 승인 흐름과 활동 로그
- 조직용 간트차트와 리소스 관리
- 고객 관계 관리
- 실시간 서버 동기화가 필수인 팀

## 3. 해결하려는 문제

플래너 이탈 원인은 다음 아홉 범주로 정리한다.

1. 성취 소실
2. 조작 마찰
3. 계획 복구 비용
4. 반쪽짜리 기능
5. 정보 가시성 부족
6. 시스템 관리 부담
7. 개인 구조와 도구 구조의 불일치
8. 데이터 신뢰 붕괴
9. 미완료에 대한 자기평가 압박

제품은 이를 다음 네 문장으로 해결한다.

1. 빠르게 기록하고 쉽게 수정한다.
2. 계획이 틀어져도 기존 기록을 버리지 않고 이어간다.
3. 미완료는 실패로 처벌하지 않고 완료는 기록으로 남긴다.
4. 다음 행동·진행 흐름·완료 흔적을 한 시스템에서 확인한다.

## 4. 닷닷 3원칙

1. **시작 전 선택을 요구하지 않는다.**
   - 빠른 입력의 기본값이 존재한다.
   - 프로젝트·그룹·시간·상세 입력은 필요할 때만 추가한다.

2. **유지 관리를 요구하지 않는다.**
   - 화면마다 기록을 복제하지 않는다.
   - 같은 정보는 연결과 조회로 재사용한다.
   - 불필요한 폴더·태그·설정 노동을 강제하지 않는다.

3. **죄책감을 주지 않는다.**
   - 빨간 연체 경고, 스트릭, 실패 문구를 핵심 표현으로 사용하지 않는다.
   - 미완료는 이동·이월·보관 가능한 상태다.
   - 완료 기록은 제자리 또는 조회 가능한 기록으로 남긴다.

## 5. 제품 구조의 여섯 축

### 5.1 단일 기록·다중 문맥

`state.items`의 항목은 Today·Weekly·Monthly Log에서 같은 ID를 유지한다.  
화면이 바뀌어도 별도 항목으로 다시 입력하지 않는다.

예외적으로 `monthlyItems`는 날짜 없는 월간 마스터 컬렉션이다. 날짜에 배치하면 `state.items`에 배치본이 생기지만 `sourceMonthlyItemId`로 원본과 연결된다.

### 5.2 시간 범위에 따른 점진적 구체화

- 이달의 할 일: 날짜를 정하지 않은 월간 후보
- Monthly Log: 월 전체의 시각적 배치
- Weekly: 가까운 날짜 비교
- Today: 실제 실행과 완료

사용자는 처음부터 날짜·시간·프로젝트를 모두 결정하지 않아도 된다.

### 5.3 계획 복구

- 완료되지 않은 과거 할 일은 이월 대상이 된다.
- 완료 항목은 자동 이월하지 않는다.
- 다일 항목은 종료일이 지난 뒤에만 이월한다.
- 삭제는 휴지통을 거쳐 복원할 수 있다.
- 이동·삭제·완료·정렬은 Undo/Redo 대상이다.

### 5.4 시각적 배치와 직접 조작

- Daily·Weekly·Monthly Log 간 드래그
- Monthly Log 실시간 하드 스냅
- 단일·가로·세로·대각선 범위 생성
- 마퀴 다중선택
- 그룹·정렬·복사·붙여넣기
- 행 높이·셀 너비·구분선 조절

직접 조작은 마우스를 자유롭게 따라가는 장식이 아니라 실제 데이터 위치와 즉시 일치해야 한다.

### 5.5 맥락 보존

- 프로젝트
- 그룹
- 연결 인스턴스
- 월간 마스터와 배치본
- 상세 설명 블록
- 하위 할 일
- 이미지·동영상

제목만 남기는 얇은 투두가 아니라, 실행에 필요한 맥락을 같은 항목 안에 보존한다.

### 5.6 로컬 데이터 신뢰

- 서버·계정 없이 로컬에서 작동
- localStorage에 구조화 데이터 저장
- IndexedDB에 첨부 파일 저장
- 저장 실패 배너
- 손상 원본 백업과 개별 격리
- 교차 탭 충돌 감지
- JSON 내보내기
- 마이그레이션 전 백업

## 6. 현재 제품 범위

### 구현 완료 범위

- Today
- 미니 달력
- Weekly 1~14일
- Calendar / Monthly Log
- 이달의 할 일
- 휴지통
- 상세 패널과 미디어
- 할 일·일정·메모·구분선
- 날짜 범위·시간·하루 종일
- 완료·완료 숨기기·완료 정리
- 이월
- 그룹
- 프로젝트 최소 축
- 일반 복사와 연결 인스턴스 복사
- 다중 선택
- 드래그·하드 스냅
- Undo/Redo
- 음력
- 라이트·다크 테마
- 저장 안전장치와 JSON 내보내기

### 화면에 아이콘만 있고 제품 범위로 확정되지 않은 항목

- 루틴
- 단축키 전용 화면
- 검색 전용 화면
- 통계 전용 화면
- 설정 전용 화면

이 항목들은 현재 사이드바에 시각적 자리만 있을 수 있다. 기능이 실제로 연결되기 전까지 구현 완료로 간주하지 않는다.

### 설계 보류 범위

- Monthly Log 24시간 축
- 종일·시간 미정 트랙
- 자정 넘김 시간 일정
- 기존 18칸 데이터의 시간축 전환
- JSON 가져오기
- IndexedDB 첨부를 포함한 완전 백업
- 3개월 이상 미완료 정책
- 열별 개별 너비
- 프로젝트 전용 화면
- 태그·검색·필터
- AM/PM 없는 시간 입력 해석

## 7. 기능 채택 판정기

새 기능은 아래 순서로 판정한다.

### Q1. 핵심 루프를 강화하는가?

`기록 → 조망 → 이동·수정 → 실행 → 완료 흔적 보존`

강화하지 않으면 기본 범위에서 제외한다.

### Q2. 재입력이나 유지 노동을 줄이는가?

같은 내용을 다시 쓰게 하거나 별도 정리를 요구하면 기각 또는 재설계한다.

### Q3. 기존 데이터 정체성을 보존하는가?

화면 전환·드래그·복사·이월 때문에 항목의 연결과 상세 정보가 사라지면 채택하지 않는다.

### Q4. 조작 문법을 깨지 않는가?

같은 클릭·드래그·단축키가 화면마다 다른 의미가 되면 채택하지 않는다.

### Q5. 안전하게 되돌릴 수 있는가?

데이터 변경은 Undo/Redo·휴지통·백업 중 적절한 복구 경로가 있어야 한다.

## 8. 설계 금칙

- 빨간 기한 초과 경고와 실패 낙인
- 스트릭과 빈 날짜 압박
- 입력 전 분류·프로젝트·우선순위 강제
- 완료·저장 후 불필요한 재확인
- 데이터 이동을 가장한 중복 복제
- 화면마다 다른 생성 규칙
- 주요 입력창과 주요 조작을 호버에만 숨기기
- 시간·날짜를 임의로 추측해 자동 수정
- 기존 기능을 확인 없이 되돌리는 대규모 리팩터링
- 테스트를 통과시키기 위한 조건 약화

## 9. 성공 기준

제품이 성공하려면 기능 수가 아니라 다음이 확인되어야 한다.

- 첫 기록까지 설명 없이 도달한다.
- 같은 기록을 여러 화면에서 다시 적지 않는다.
- 계획 변경 후에도 시스템을 버리지 않는다.
- 완료와 과거 기록을 다시 찾을 수 있다.
- 데이터 저장 실패를 사용자가 인지할 수 있다.
- 사용자가 앱 관리보다 실제 계획에 더 많은 시간을 쓴다.
